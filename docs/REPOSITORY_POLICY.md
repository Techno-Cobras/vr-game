# Политика хранения Unity-проекта

## Статус и область действия

Этот документ закрывает задачу #6 и задаёт обязательные правила репозитория до
создания Unity-проекта в задаче #8. Технологический baseline описан в
[ADR 0005](adr/0005-vr-technology-stack.md), но сами `Assets/`, `Packages/` и
`ProjectSettings/` пока не добавлены.

Политика применяется ко всем изменениям Unity-проекта. Источником истины служат
файлы, которые можно восстановить из Git и Git LFS; локальные кэши и результаты
сборки в репозиторий не попадают.

## Что хранится в Git

| Путь или тип | Правило |
| --- | --- |
| `Assets/**` и соответствующие `*.meta` | Коммитятся вместе. Исключение — только явно документированные генерируемые файлы. |
| `Packages/manifest.json` и `Packages/packages-lock.json` | Коммитятся и изменяются одним PR через Unity Package Manager. |
| `ProjectSettings/**` | Коммитится; изменения должны соответствовать выбранной версии Unity. |
| `.gitignore`, `.gitattributes`, документация и скрипты | Коммитятся как обычный текст с LF. |
| Двоичные изображения, модели, аудио, видео, шрифты и нативные библиотеки | Коммитятся через Git LFS по шаблонам из `.gitattributes`. |

Корневые каталоги `Library/`, `Temp/`, `Obj/`, `Build/`, `Builds/`, `Logs/`,
`UserSettings/`, `MemoryCaptures/`, `Recordings/` и `UIElementsSchema/` являются
локальными или воспроизводимыми и игнорируются. То же относится к локальным
`.gradle/`, `.utmp/` и временным `*.utmp`. Также игнорируются файлы IDE,
журналы, дампы, metadata генерируемых debug-файлов и готовые Android-сборки.
Папки `Assets/`, `Packages/` и `ProjectSettings/`, а также `*.meta`, нельзя
добавлять в `.gitignore` целиком.

## Сериализация Unity и metadata

При создании проекта в Unity Editor необходимо включить:

- `Version Control Mode = Visible Meta Files`;
- `Asset Serialization Mode = Force Text`.

Настройки должны быть сохранены самим Editor в `ProjectSettings`, а не
сымитированы вручную до появления проекта. Каждый ассет и его `*.meta`
добавляются, перемещаются и удаляются в одном коммите. GUID из `*.meta`
идентифицирует ассет: нельзя пересоздавать, копировать или произвольно выбирать
GUID для разрешения конфликта. Пустые каталоги `Assets/` не фиксируются через
`.gitkeep`, потому что Unity создаёт для такого файла отдельный metadata-ассет.

Текстовые сериализованные файлы Unity (`*.unity`, `*.prefab`, `*.asset`,
`*.mat`, `*.anim`, `*.controller` и `*.meta`) остаются обычными текстовыми
файлами, а не объектами LFS. Это сохраняет обозримые diff и возможность
семантического разрешения конфликтов.

## Git LFS

Git LFS обязателен для двоичных ассетов следующих категорий:

- текстуры и исходники изображений: PNG, JPEG, TGA, TIFF, PSD/PSB, EXR, HDR, DDS;
- модели: FBX, Blend, GLB, OBJ;
- аудио: WAV, MP3, OGG, FLAC, AIF/AIFF;
- видео: MP4, MOV, WebM;
- шрифты: TTF, OTF;
- нативные плагины: DLL, SO, DYLIB, Bundle.

Шаблоны регистронезависимы, поэтому `PNG` и `png` обрабатываются одинаково.
Перед началом работы разработчик выполняет `git lfs install`, после получения
изменений — `git lfs pull`. Новые категории добавляются в `.gitattributes` до
первого коммита соответствующего двоичного файла.

Атрибут `lockable` пока не используется: его можно включить отдельным решением
после проверки поддержки locks на remote и процесса команды. Миграция уже
опубликованной истории в LFS также требует отдельного согласования и не должна
выполняться незаметно в обычном PR.

## Владение конфликтными файлами

Перед изменением автор объявляет владельца в задаче или PR. Одновременно один
активный владелец допускается для каждой конфликтной области:

| Область | Правило владения |
| --- | --- |
| `ProjectSettings/**` | Один владелец фундаментальных настроек на PR; несвязанные правки разделяются. |
| Оба файла `Packages/*.json` | Один владелец зависимостей; одновременно выполняется один dependency PR. |
| Сцена `*.unity` | Один владелец каждой сцены; крупный мир заранее делится на additive-сцены. |
| Prefab и его варианты | Один активный редактор для семейства prefab. |
| Двоичный LFS-ассет | Один активный редактор; параллельные варианты создаются отдельными файлами. |
| Input Actions и другие общие serialized assets | Один владелец файла на время изменения. |

## Разрешение конфликтов

1. Получить свежий `origin/main` и синхронизировать task branch до продолжения
   редактирования.
2. Для текстовых сцен, prefab и других Unity YAML применить `UnityYAMLMerge`
   (Smart Merge), когда его путь будет известен из установленной версии Unity.
   Merge driver настраивается локально; непереносимая абсолютная команда не
   записывается в `.gitattributes`.
3. Открыть результат в точной версии Unity из ADR 0005, дождаться импорта и
   проверить Console, отсутствующие ссылки и затронутые сценарии.
4. `ProjectSettings` объединять по смыслу, а не выбором целой стороны. Конфликт
   package manifest разрешать через ожидаемый набор зависимостей, после чего
   lock-файл регенерировать Unity Package Manager.
5. Для `*.meta` сохранить GUID того логического ассета, на который уже ссылается
   проект. Нельзя слепо применять `ours` или `theirs`.
6. Двоичные файлы не объединяются: назначенный владелец повторяет изменение
   поверх актуальной версии или сохраняет осознанно названные варианты.

## Проверка и onboarding

После клонирования:

```powershell
git lfs install
git lfs pull
pwsh -NoProfile -File scripts/Test-RepositoryPolicy.ps1
```

Скрипт без создания fixture-файлов проверяет ожидаемые результаты
`git check-ignore`, текстовые и LFS-атрибуты через `git check-attr`, а также
доступность Git LFS. Его необходимо запускать после изменений `.gitignore`,
`.gitattributes` или этой политики.

Unity build и PlayMode/EditMode tests пока невозможны: проект появится в задаче
#8. После этого проверенные команды должны быть добавлены в
`docs/ARCHITECTURE.md` и CI.
